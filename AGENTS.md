# ARK-OS AI Rules and Engineering Regulations

**Project:** ARK-OS  
**Primary technologies:** Swift, C, C++, Linux, shell scripting, and architecture-specific low-level code  
**Primary objective:** Maintain a modular, understandable, reliable, maintainable, and reproducible operating-system project.

These rules are mandatory for every AI agent contributing to ARK-OS, regardless of model, tool, or task.

The purpose of this document is to prevent unnecessary complexity, duplicated code, undocumented changes, uncontrolled file creation, misleading documentation, and modifications that break existing functionality.

The priority order is:

1. Correctness and preservation of existing functionality.
2. Security and system stability.
3. Minimal, focused changes.
4. Clear architecture and maintainability.
5. Accurate documentation and reproducibility.
6. Performance and resource efficiency where relevant.

Do not sacrifice correctness or maintainability merely to produce a shorter answer or finish a task faster.

---

# 1. General Engineering Principles

## 1.1 Write Good Code

- Write code that is correct, readable, maintainable, and appropriate for its purpose.
- Prefer simple, direct implementations over unnecessarily clever abstractions.
- Follow the established coding style and architecture of the component being modified.
- Use meaningful names for variables, functions, types, files, and modules.
- Keep functions and types focused on a clearly defined responsibility.
- Avoid unnecessary nesting, deeply coupled components, duplicated logic, and excessively long functions.
- Handle errors explicitly and appropriately. Do not silently ignore failures.
- Do not introduce global mutable state unless the architecture genuinely requires it.
- Avoid force operations, unchecked assumptions, unsafe memory access, and undefined behavior unless they are necessary for a documented low-level requirement.
- When unsafe operations are unavoidable, minimize their scope and explain the safety invariants.
- Use appropriate abstractions, not abstractions for their own sake.
- Follow established language conventions and official language guidance where applicable.
- Never make code artificially complicated to make it appear sophisticated.

## 1.2 Do Not Bloatify the Codebase

The word *bloat* includes unnecessary implementation, redundant files, excessive abstractions, pointless configuration, duplicated dependencies, and features that nobody requested.

- Do not add functionality unrelated to the requested task.
- Do not introduce frameworks, dependencies, helper layers, managers, registries, factories, or plugins without a concrete requirement.
- Do not create a generalized solution when a small, local fix solves the actual problem.
- Do not duplicate existing functionality. Find and reuse the appropriate existing implementation.
- Do not create multiple implementations of the same feature merely to avoid understanding the original.
- Do not add speculative future-proofing, unused extension points, or compatibility layers without a demonstrated need.
- Do not add excessive validation for impossible states when the relevant invariants are already enforced. Do validate untrusted inputs and external boundaries.
- Do not create empty directories, placeholder implementations, empty source files, or unused configuration files.
- Do not add comments that merely restate the code.
- Do not add tests that assert nothing meaningful or simply duplicate implementation details.
- Do not perform unrelated refactoring during a bug fix.
- Do not rewrite working code solely because another implementation looks more appealing.

**Rule:** Every addition must have a clear purpose connected to the requested task or an explicitly approved engineering requirement.

## 1.3 No Emojis

The use of emojis is strictly prohibited in:

- Source code comments.
- Documentation.
- Commit messages.
- Log messages.
- Error messages.
- Terminal output generated by project tools.
- AI-generated reports and checklists.
- Identifiers, filenames, and configuration values.

Use clear words, conventional symbols, and meaningful labels instead.

## 1.4 No Meaningless Hype

Do not use exaggerated, childish, promotional, or meaningless expressions such as:

- Mega, Ultra, God-tier, Insane, Beast Mode, or similar language.
- Industry-grade, enterprise-grade, military-grade, production-ready, or revolutionary without specific, verifiable justification.
- Claims that code is flawless, invincible, unbreakable, perfectly optimized, or completely secure.

Use precise technical descriptions.

For example:

Incorrect: "This is an ultra-powerful, industry-grade kernel optimization."

Correct: "This change reduces repeated memory allocations in the affected code path."

Only make performance or security claims when evidence supports them.

## 1.5 Maintain a Consistent Tone

- Use a professional, direct, technically accurate tone.
- Do not suddenly change writing style between sections or responses.
- Do not use unnecessary jokes, marketing language, excessive enthusiasm, or conversational filler in project documentation.
- Match the existing style of the file being modified.
- Keep technical explanations understandable without sacrificing accuracy.

# 2. Questions, Assumptions, Plans, and Checklists

## 2.1 Understand Before Acting

Never guess when an incorrect assumption could change architecture, public interfaces, system behavior, security, data integrity, or compatibility.

Before modifying code:

1. Identify the requested outcome.
2. Identify the component responsible for that behavior.
3. Inspect the relevant implementation and its direct dependencies.
4. Check existing documentation, interfaces, configuration, and tests where relevant.
5. Identify constraints and potential regressions.
6. Ask a concise clarifying question if a material ambiguity cannot be resolved from the repository or request.

Do not ask unnecessary questions when the answer is already available in the codebase or documentation.

When a reasonable, low-risk assumption is sufficient, state it explicitly and proceed if the task permits it.

Never silently invent requirements.

## 2.2 Prepare a Plan Before Making Changes

Before editing, provide a concise plan containing:

- **Objective:** What needs to change.
- **Findings:** What the existing code currently does and what is wrong or missing.
- **Files:** The exact files expected to change.
- **Reason:** Why each file needs modification.
- **Approach:** How the change will solve the problem.
- **Risks:** Any relevant compatibility, architecture, or regression concerns.
- **Validation:** What will be inspected or tested, subject to the build-command restrictions below.

Do not list speculative files as though they definitely need modification.

If investigation reveals that the plan must change, explain the reason before making substantial additional changes.

## 2.3 Maintain an Accurate Checklist

For tasks involving multiple steps, maintain a checklist with three sections:

### Pending
Work that has not started.

### In progress
Work currently being performed.

### Completed
Work that has actually been completed and inspected.

Update the checklist as work progresses.

Never mark an item complete merely because code was generated or a command was suggested.

If an item cannot be completed, mark it as blocked or not completed and explain why.

Do not create a permanent checklist file for every small task. Use the response unless the user explicitly requests a project-tracked checklist.

## 2.4 Never Pretend Work Is Complete

- Never claim a file was edited unless it was actually edited.
- Never claim a test passed unless its result was observed.
- Never claim a build succeeded unless the build actually ran and completed successfully.
- Never claim a bug is fixed without adequate evidence.
- Never claim documentation is current without checking the relevant implementation.
- Never hide incomplete work, skipped steps, warnings, or known limitations.
- Never fabricate command output, test results, benchmark numbers, or validation reports.

Distinguish clearly between implemented, inspected, tested, and verified.

# 3. Repository Structure and File Ownership

The repository root is reserved for essential project-level files and explicitly approved directories.

Do not create arbitrary files or directories in the root.

The existing directory structure defines the intended ownership boundaries.

## 3.1 `components/`

Contains first-party ARK-OS software organized by responsibility.

### `components/apps/`

Contains applications that run on ARK-OS.

Rules:

- Each application must have a clear purpose and defined entry point.
- Shared functionality belongs in an appropriate existing library.
- Applications must not duplicate core system functionality without justification.
- Application-specific resources must remain within the owning application.
- Do not place unrelated services, compiler tools, kernel code, or upstream source trees here.

### `components/boot/`

Contains first-party boot components and boot-related implementations.

Rules:

- Keep boot-stage responsibilities distinct.
- Document required execution environments and handoff contracts.
- Preserve boot protocol and memory-layout requirements.
- Architecture-specific code must be clearly separated when necessary.
- Do not place unrelated host-side compilation scripts here.
- Never modify the boot sequence speculatively without understanding the current handoff and failure behavior.

### `components/libraries/libark/`

Contains the first-party `libark` library and its public interfaces.

Rules:

- Keep the public API intentional, minimal, and documented.
- Place implementation details behind the public API when appropriate.
- Do not turn `libark` into a miscellaneous collection of unrelated utilities.
- Avoid circular dependencies.
- Do not introduce dependencies on applications or high-level services.
- Add functionality only when it belongs to the library's defined responsibility.
- Preserve API compatibility unless a breaking change is explicitly approved.
- Document ownership, lifetimes, error behavior, and concurrency requirements where relevant.

### `components/runtime/arkrt/`

Contains the first-party ARK-OS runtime and initialization process.

Rules:

- Keep initialization, process lifecycle, and runtime responsibilities clearly defined.
- Do not place unrelated applications, shell commands, or host build logic here.
- Minimize dependencies required during early startup.
- Make startup failures diagnosable.
- Preserve the established startup sequence unless a change is required and understood.
- Do not assume that facilities available in a normal Linux userspace are available during early boot.
- Document required kernel interfaces and runtime assumptions.

### `components/services/`

Contains system services that provide functionality to other system components.

Rules:

- Each service must have a distinct responsibility.
- Define communication interfaces and lifecycle expectations.
- Keep service implementations separate from application-specific behavior.
- Validate untrusted inputs at service boundaries.
- Avoid unnecessary inter-service dependencies and circular communication.
- Do not duplicate functionality already provided by an existing service without justification.

### `components/shell/sash/`

Contains the first-party `sash` shell.

Rules:

- Keep command parsing, execution, built-ins, and user-facing behavior organized around clear responsibilities.
- Preserve existing command behavior unless a change is requested.
- Do not implement unrelated system services inside the shell.
- Reuse suitable `libark` functionality rather than copying its implementation.
- Handle malformed input and execution failures predictably.
- Keep shell-specific code independent of unrelated applications.
- Do not claim compatibility with Bash, POSIX shell, or another shell unless the relevant behavior is implemented and verified.

## 3.2 `host-tools/`

Contains tools that execute on the development host rather than as part of the target operating system.

### `host-tools/aake/`

Contains Aake, the ARK-OS compilation and build orchestration tool.

Rules:

- Keep build orchestration separate from target operating-system implementations.
- Represent dependencies and target selection explicitly.
- Reuse the existing build systems of upstream projects where appropriate.
- Do not duplicate compiler or linker functionality without a concrete requirement.
- Keep build output outside tracked source directories.
- Make build failures visible and actionable.
- Do not silently ignore failed subprocesses or missing dependencies.
- Preserve deterministic build behavior where practical.
- Never introduce arbitrary filesystem modifications as an undocumented side effect of a build operation.

### `host-tools/signing/`

Contains maintained host-side signing and verification tools.

Rules:

- Clearly distinguish test keys from production keys.
- Never commit private signing keys, secrets, tokens, or credentials.
- Never generate or replace production signing material without explicit authorization.
- Document supported formats, trust assumptions, and verification behavior.
- Fail safely when verification fails.

## 3.3 `devtools/`

Contains maintained developer utilities that support repository development and maintenance.

### `devtools/check/`

Contains repository checks, structural validation, static checks, and related maintenance utilities.

Rules:

- Checks should be deterministic and narrowly scoped.
- Prefer read-only validation by default.
- Do not silently modify files during validation.
- Report the exact file or rule that failed.
- Avoid duplicate checkers that perform the same work.
- Do not create a new script for every individual task.
- Do not build a custom linter when a suitable existing tool meets the requirement.

### `devtools/release/`

Contains maintained release preparation and verification utilities.

Rules:

- Do not publish, upload, sign, tag, or distribute a release without explicit authorization.
- Validate release inputs and versions.
- Do not include secrets or unintended development artifacts.
- Keep release steps reproducible and documented.
- Clearly report actions that were prepared but not executed.

## 3.4 `docs/`

Contains the canonical project documentation.

### `docs/architecture/`

Documents component responsibilities, dependency direction, interfaces, boot flow, memory ownership, process boundaries, and other architectural decisions.

### `docs/bringup/`

Documents hardware bring-up, emulator setup, boot diagnostics, serial output, display initialization, and platform-specific debugging procedures.

### `docs/decisions/`

Contains architecture decision records.

Each significant decision should document:

- Context and problem.
- Considered alternatives.

Do not rewrite historical decisions merely to make the current implementation appear intentional. Record superseding decisions when appropriate.

### `docs/development/`

Contains contributor setup, development workflows, code conventions, dependency management, and maintenance procedures.

### `docs/licensing/`

Contains licensing policy, attribution guidance, compliance procedures, and related documentation.

Rules for all documentation:

- Documentation must describe the actual implementation.
- Update relevant documentation when behavior, configuration, interfaces, or workflows change.
- Do not duplicate the same canonical instructions across multiple files.
- Prefer linking to the authoritative document.
- Do not invent commands, options, APIs, supported platforms, or prerequisites.
- Mark unimplemented features and experimental functionality accurately.
- Remove obsolete instructions when their replacement is established.
- Do not create a document when a short addition to an existing document is sufficient.

## 3.5 `external/`

Contains or coordinates external upstream projects and dependencies when they are required.

Rules:

- Prefer pinned revisions and reproducible retrieval methods.
- Record upstream URLs, revisions, licenses, and local patches.
- Do not silently replace an upstream revision.
- Do not copy an entire external project into a first-party component.
- Do not modify upstream code directly without identifying the change and its maintenance implications.
- Keep local patches small, reviewable, and associated with the correct upstream project.
- Follow the upstream project's license and contribution requirements.
- Do not download or vendor an entire dependency when only a compatible package or a small, permitted dependency is required.

The exact external checkout mechanism may vary by project. Use Git submodules, pinned source archives, or another documented mechanism appropriate to the dependency.

Contains authoritative build and dependency declarations.

### `manifests/components.toml`

Defines the first-party components and their metadata, dependencies, locations, and other explicitly supported fields.

### `manifests/sources.lock.toml`

Records pinned external source revisions or other locked source identifiers according to the project's chosen schema.

### `manifests/targets/`

Contains target-specific configuration.

- `x86_64.toml` defines the x86_64 target.
- `arm64.toml` defines the ARM64 target.

Rules:

- Follow the existing schema.
- Do not invent fields without updating the schema and every relevant consumer.
- Validate references and reject unknown or missing required fields.
- Avoid duplicating the same source of truth across multiple manifests.
- Never silently fall back to an unintended target or dependency version.
- Document the meaning of non-obvious configuration values.
- Keep target-specific configuration separate from genuinely shared configuration.

## 3.7 `packaging/`

Contains system-image assembly and packaging definitions.

### `packaging/recipes/`

Contains explicit recipes for assembling or preparing packages and system components.

### `packaging/rootfs/`

Contains the intended root filesystem layout, metadata, and maintained configuration required for assembling the root filesystem.

Rules:

- Distinguish source files from generated filesystem contents.
- Do not commit generated images or build outputs unless explicitly required.
- Do not place arbitrary host configuration files into the target filesystem.
- Document where system files originate and which component owns them.
- Avoid including unnecessary utilities, dependencies, or services in the final image.
- Preserve file permissions, ownership, and required metadata.
- Do not claim an image is bootable until its relevant validation has actually been performed.

## 3.8 `sdk/`

Reserved for the ARK-OS Software Development Kit.

Only add SDK components when an actual SDK is being designed or implemented.

Potential contents include documented development headers, supported libraries, target metadata, toolchain integration, and distribution packaging.

Rules:

- Do not duplicate `host-tools/` or upstream compiler sources unnecessarily.
- Distinguish host-side SDK utilities from target-side runtime components.
- Document supported target architectures and compatibility expectations.
- Do not advertise an SDK as available when it is incomplete or untested.
- If the SDK has not yet been defined, leave the directory absent rather than inventing its contents.

## 3.9 `tests/`

Contains tests organized by scope.

### `tests/unit/`

Tests individual functions, modules, and isolated behaviors.

### `tests/integration/`

Tests interactions between components and their interfaces.

### `tests/boot/`

Tests boot behavior, startup assumptions, and relevant system integration paths.

Rules:

- Tests must verify meaningful behavior.
- Prefer testing public contracts and observable outcomes.
- Add regression tests for reproducible bugs when practical.
- Do not weaken or delete an existing test merely to make a change appear successful.
- Do not introduce tests that depend on unspecified host state.
- Document hardware or environment requirements for tests that cannot run everywhere.
- Never report a test as passed when it was not executed.

## 3.10 Root-Level Files

- `AGENTS.md`: Mandatory AI engineering and repository rules.
- `CONTRIBUTING.md`: Human contribution workflow, review requirements, and contribution conventions.

# 4. Code Comments and Documentation

## 4.1 Write Comments That Explain Something Useful

Comments must be accurate, concise, relevant, and maintained alongside the code.

Good comments explain:

- Why a non-obvious decision was made.
- Which invariant must remain true.
- Why a seemingly unnecessary operation is required.
- Important ownership or lifetime constraints.
- Hardware or architecture-specific behavior.
- Compatibility workarounds and their conditions.
- Security assumptions and relevant failure modes.
- Non-obvious algorithmic choices.

Avoid comments that simply translate code into English.

Bad:

```swift
// Increment the counter by one.
counter += 1
```

Better, when the reason is genuinely non-obvious:

```swift
// Reserve the identifier before dispatch so concurrent requests
// cannot receive the same value.
counter += 1
```

The second comment is appropriate only if that statement accurately describes the implementation.

## 4.2 Swift Documentation Comments

Use Swift documentation comments for public APIs and non-obvious contracts.

Example:

```swift
/// Resolves a path relative to the configured root directory.
///
/// - Parameter path: The path to resolve.
/// - Returns: The resolved path, if it satisfies the resolution rules.
/// - Throws: An error if the path cannot be resolved safely.
public func resolvePath(_ path: String) throws -> String {
    // Implementation.
}
```

This is an illustrative API contract, not a claim that ARK-OS already provides this function.

Rules:

- Document parameters, return values, errors, ownership, and concurrency requirements when relevant.
- Do not document nonexistent behavior.
- Keep comments synchronized with implementation changes.
- Do not add elaborate documentation to trivial private helpers when the code is already clear.
- Do not promise that a function is thread-safe, allocation-free, constant-time, or secure unless that property has been established.

## 4.3 C and C++ Comments

- Use the established comment style in the relevant source file.
- Document public headers, ownership rules, lifetime requirements, and error contracts.
- Explain pointer validity and buffer-size assumptions where necessary.
- Clearly identify hardware registers, bit fields, memory layouts, and architecture-specific invariants.
- Do not add meaningless comments to every statement.
- Never use comments to conceal unsafe behavior or unresolved defects.

## 4.4 No Fake or Stale Comments

Before modifying a function, check its existing comments and documentation.

If a change makes a comment inaccurate, update it in the same change.

Never leave comments describing deleted functionality, obsolete APIs, nonexistent files, or behavior that the implementation does not provide.

# 5. Bug Fixing and Debugging

## 5.1 Investigate the Actual Problem

When a bug or error is reported:

1. Identify the exact failure and expected behavior.
2. Find the responsible implementation.
3. Inspect its direct dependencies and relevant call sites.
4. Check recent changes or version-control history when useful.
5. Determine the smallest plausible cause.
6. Confirm the cause using available evidence.
7. Implement the smallest sufficient fix.
8. Inspect the diff for regressions and unrelated modifications.

Do not inspect the entire repository without a reason.

Do not investigate unrelated files simply because they exist.

Expand the investigation only when the evidence points to a dependency or cross-component interaction.

## 5.2 Preserve Working Behavior

If previously working functionality breaks:

- Inspect the relevant previous implementation using Git history when available.
- Compare the working and broken behavior.
- Identify the specific change that caused the regression.
- Preserve existing behavior unless it conflicts with an explicit requirement.
- Prefer restoring a known-good invariant over replacing the entire implementation.
- Do not blindly revert unrelated changes or discard uncommitted work.

Previous code is evidence, not unquestionable truth. A previous implementation may contain the same defect or an obsolete assumption.

## 5.3 Minimal Bug Fixes

A bug fix must not become an opportunity for unrelated redesign.

Do not:

- Rewrite an entire subsystem to fix a localized defect.
- Rename unrelated files.
- Change APIs unnecessarily.
- Add unrelated features.
- Introduce a new dependency for a problem that existing code can solve.
- Reformat an entire file to change a few lines.
- Replace a working implementation without evidence that replacement is necessary.

If a larger redesign is genuinely required, explain why and obtain approval before expanding the task.

## 5.4 Follow Evidence

- Distinguish observed facts from hypotheses.
- Do not repeatedly guess different fixes without learning from previous results.
- Use relevant logs, error messages, call paths, configuration, and history.
- Do not suppress an error simply to make it disappear.
- Do not add arbitrary delays, retries, or fallback behavior without understanding the failure.
- Do not report a root cause as confirmed when the available evidence only suggests it.

# 6. Build and Command Execution Restrictions

**Never run build commands unless the user explicitly authorizes them.**

This includes commands that compile, link, package, or generate build artifacts, such as:

- `swift build`
- `swift test`
- `make`
- `ninja`
- `cmake --build`
- Project-specific Aake build commands.
- Kernel compilation.
- Firmware compilation.
- System-image assembly.

Do not evade this rule by invoking a build through a shell script, IDE task, helper tool, or another command.

Instead:

- Inspect source code and configuration where possible.
- Perform read-only analysis when appropriate.
- Explain which build or test command the user should execute.
- Describe what the result would establish.
- Clearly state that runtime or compilation behavior remains unverified.

If the user explicitly authorizes a build, execute only the relevant authorized operation and report the actual result.

Do not run destructive cleanup, deployment, signing, flashing, publishing, or other consequential operations without explicit authorization.

Read-only inspection commands may be used when relevant and permitted. Do not treat a command as harmless solely because its name sounds familiar; understand its effects first.

# 7. Swift Engineering Rules

- Follow the established Swift language version and supported toolchain.
- Use clear names and appropriate access control.
- Prefer value types when they accurately model the data and lifecycle.
- Use reference types when identity or shared mutable state is required.
- Avoid unnecessary protocol hierarchies, generics, property wrappers, and abstractions.
- Avoid force unwrapping and forced error handling unless the invariant is established and the operation is genuinely justified.
- Do not swallow errors with empty `catch` blocks.
- Use `throws`, typed errors where appropriate, or another explicit failure mechanism consistent with the surrounding code.
- Respect actor isolation and concurrency-safety requirements when concurrency is used.
- Do not claim `Sendable` conformance or thread safety without satisfying the relevant invariants.
- Avoid unnecessary heap allocations, copies, and repeated conversions in performance-sensitive code.
- Measure or establish the relevant performance problem before introducing complicated optimizations.
- Keep public APIs small and intentional.
- Do not assume Foundation, Dispatch, SwiftUI, or other Apple frameworks are available on every Linux target.
- Check actual Linux support, toolchain availability, linking requirements, and target compatibility before introducing framework dependencies.
- Keep host-side tools separate from target-side code.
- Never confuse SwiftPM package organization with the requirements of a freestanding runtime, kernel, bootloader, or custom target environment.

Do not introduce a dependency simply because it is an Apple open-source project. Verify that it fits the target environment and license requirements.

# 8. C, C++, Kernel, and Low-Level System Rules

- Follow the existing kernel, bootloader, firmware, or subsystem conventions.
- Preserve ABI, calling conventions, memory layouts, alignment, and required execution assumptions.
- Respect interrupt context, locking rules, reentrancy, and concurrency constraints.
- Do not assume dynamic allocation, exceptions, RTTI, threads, or standard-library facilities are available in freestanding environments.
- Do not introduce floating-point operations into contexts where they are unsupported or unsafe.
- Validate buffer lengths, integer conversions, pointer lifetimes, and alignment where relevant.
- Avoid undefined behavior and data races.
- Use volatile, atomics, memory barriers, and synchronization primitives according to their actual semantics. They are not interchangeable.
- Do not assume `volatile` provides thread synchronization.
- Preserve required compiler and linker flags.
- Document non-obvious architecture-specific assumptions.
- Keep assembly and hardware-specific code as small and isolated as practical.
- Do not invent hardware registers, memory maps, kernel interfaces, boot protocols, or device capabilities.
- Do not change kernel configuration, boot protocol, or memory layout without examining the actual target requirements.

Any unsafe or architecture-specific change must have a clear technical justification.

# 9. Linux and Operating-System Rules

- Understand the difference between host Linux, target Linux, a custom runtime, and a freestanding execution environment.
- Do not assume a userspace API exists in the kernel or early boot environment.
- Do not assume a service manager, shell, dynamic linker, filesystem, network stack, or standard utility exists unless the target actually provides it.
- Respect process boundaries, permissions, file descriptors, signals, system calls, and resource lifetimes.
- Handle failures from system calls and external interfaces appropriately.
- Do not run commands that modify the host system without authorization.
- Do not modify host boot configuration, mount filesystems, change device permissions, or flash hardware as an incidental side effect.
- Avoid hard-coded host paths, user-specific paths, and environment assumptions.
- Keep target-specific paths and settings configurable where appropriate.
- Preserve the distinction between build-time dependencies and runtime dependencies.
- Do not add a dependency to the final system image when it is only required by the development host.

4. Verify available commands and options from their definitions.
5. Distinguish implemented functionality from planned work.
6. Update obsolete instructions when a change makes them incorrect.

- Claim support for an architecture that has not been established.
- Advertise an unimplemented command.
- Claim performance improvements without evidence.
- List dependencies that are not actually required.
- Present a planned milestone as a completed capability.

# 12. Security and Reliability

- Treat external inputs, filesystem paths, configuration, network messages, and inter-process communication as potentially untrusted.
- Validate inputs at appropriate boundaries.
- Avoid unsafe deserialization, command injection, path traversal, and accidental privilege escalation.
- Never hard-code secrets or credentials.
- Do not disable security checks simply to bypass an error.
- Do not suppress warnings without understanding their cause.
- Preserve least-privilege behavior.
- Use explicit permission and ownership requirements.
- Consider resource exhaustion, failure recovery, and cleanup where relevant.
- Avoid logging secrets or sensitive data.
- Do not claim that a component is secure solely because it compiles or passes a small test suite.
- Do not make security-sensitive changes outside the task's scope without explaining the risk and obtaining approval where required.

Security fixes should be focused, evidence-based, and reviewed carefully.

---

# 13. Performance and Resource Efficiency

ARK-OS targets environments where memory, storage, boot time, and CPU usage may be constrained.

- Avoid unnecessary allocations and copies in measured or demonstrably sensitive code paths.
- Avoid repeated parsing, initialization, or filesystem work when it is unnecessary.
- Keep startup dependencies and early-boot responsibilities minimal.
- Avoid spawning processes or threads without a concrete need.
- Prefer straightforward algorithms with suitable complexity.
- Do not introduce caches without a clear invalidation and ownership strategy.
- Do not optimize code based solely on appearance.
- Do not sacrifice correctness, memory safety, or maintainability for speculative performance gains.
- Do not claim a memory reduction, faster boot, or lower CPU usage without relevant evidence.
- Consider the effect of dependencies on the final system image, not only the host development environment.

# 15. File Creation, Deletion, and Modification

Before creating a file:

- Determine whether an existing file already serves the same purpose.
- Identify the directory responsible for the functionality.
- Confirm that the file is needed for the requested change.
- Follow existing naming and organization conventions.

Before deleting a file:

- Check its references and responsibilities.
- Determine whether it is used by manifests, build scripts, documentation, tests, or release tooling.
- Preserve any unique functionality that must remain.
- Obtain authorization for significant deletions or broad cleanup.

Before renaming or moving a file:

- Check imports, references, configuration, documentation, and tooling.
- Avoid combining large-scale moves with unrelated implementation changes.

Never:

- Create duplicate files to avoid editing the original.
- Leave backup copies such as `file_old`, `file_new`, `file_fixed`, or `file_final`.
- Create numbered versions of scripts for one-off experiments.
- Scatter generated code across unrelated directories.
- add unapproved root-level files.
- Delete files simply because they appear unused without investigating their references.

Generated code is permitted only when the generation process and output location are justified and documented where necessary.

# 16. Validation and Code Review

Before presenting a completed change:

- Review every modified file.
- Inspect the final diff.
- Check for unrelated changes.
- Check for duplicated implementations and unnecessary abstractions.
- Check comments and documentation for accuracy.
- Check public interfaces and dependency changes.
- Check error handling and relevant edge cases.
- Check for accidental secrets, generated files, or licensing omissions.
- Identify which validation steps were actually performed.

Follow the build-command restrictions in Section 6.

When execution is not authorized, perform appropriate static inspection and clearly state which tests or builds remain unverified.

Do not invent successful validation results.

# 17. Required Final Report

After completing a task, provide a concise and accurate report.

Use the following format for non-trivial changes:

## Objective
The requested problem or feature.

## Changes made
The actual modifications and their purpose.

## Files modified
List every modified file and explain why it changed.

## Checklist
- [x] Items actually completed.
- [ ] Items remaining or blocked.

## Validation
State what was inspected, what was executed with authorization, and what remains unverified.

## Risks and limitations
Report known regressions, compatibility concerns, assumptions, and unresolved issues.

For small tasks, keep the report proportionately short.

Never list planned changes as completed changes.

Never omit an important limitation to make the report look successful.

# 18. Mandatory Final Rules

Before every task is considered complete, verify that the following principles have been respected:

1. The requested problem was addressed without unrelated changes.
2. The correct component owns the implementation.
3. No unnecessary features, dependencies, abstractions, files, or scripts were introduced.
4. Existing behavior was preserved unless a change was explicitly required.
5. Comments and documentation accurately describe the code.
6. No emojis or meaningless promotional language were introduced.
7. No build or destructive command was run without authorization.
8. No unverified result was presented as a fact.
9. Every changed file has a clear reason.
10. Remaining work and limitations are reported honestly.

If any rule cannot be followed, explain the reason rather than silently ignoring it.

**Final principle:** ARK-OS must remain understandable to a developer who did not write the original code and who does not have access to the AI agent that modified it. The implementation, interfaces, documentation, and version history must be sufficient to understand and maintain the system without relying on undocumented AI-generated knowledge.
